# 一人賛否ニュース 障害対応メモ

> **人間向けの復旧マニュアル。Scheduled Taskに読ませる実行ルールではない。**  
> 通常運用の正本は `docs/daily_news_rules.md`。このファイルは、事故時に「どこまで成功したか」「何を直すべきか」を確認するために使う。

## 現在の通常運用

- Scheduled Task開始：**毎日18:40 JST**
- 対象期間：**前日18:31〜当日18:30 JST**
- 18:31以降の新着：翌日分
- 18:30以降の追加新着確認：なし
- GitHub反映順：`daily → README → recent_index`
- 正本読み込み成功＋3ファイル更新成功＋整合性確認完了なら、**時刻を待たず** Issue #1へ `@karipuri` 通知
- 正本読み込みエラー、更新失敗、整合性未確認など不具合があれば通知しない

## まず最初に見るもの

事故が疑われるときは、いきなり再生成・再実行せず、次の順で確認する。

1. Scheduled Task「一人賛否ニュース」が当日実行されたか
2. チャットに本文が届いたか
3. 当日の `daily/YYYY/MM/YYYY-MM-DD.md` が更新されたか
4. `README.md` が更新されたか
5. `daily/recent_index.md` が更新されたか
6. daily・README・recent_index の内容が整合しているか
7. Issue `yuya228/news-archive#1` に当日の `@karipuri` 通知があるか

GitHubでは、**コミット時刻と差分**を見ると、どの工程まで成功したか判断しやすい。

## 基本原則

- **原因不明のまま全部作り直さない。** まず停止地点を確認する。
- **本文の事実誤認**なら、確定本文を修正し、daily・README・recent_index の影響箇所を揃える。
- **表示・転記・Markdown変換ミス**なら、確定本文を基準に該当媒体だけ直す。
- **GitHub障害・部分更新**なら、成功済みの内容を確認して不足分だけ復旧する。
- `recent_index.md` は索引であり、事実確認の根拠にはしない。
- コミット回数が多いだけでは事故と判断しない。必ず差分を見る。
- 正常更新条件が揃っていない状態で `@karipuri` 通知を追加しない。

---

## 1. 18:40を過ぎてもタスクが動かない / 19時ごろまでにニュースが来ない

### 確認

- Scheduled Taskが有効か
- 当日の実行履歴・`last_run_time` が更新されているか
- GitHubに当日のコミットがあるか
- Issue #1に当日の通知だけ出ていないか

### 見分け方

- **実行履歴もGitHub更新もない**：Scheduled Task自体が起動していない可能性
- **GitHubは更新済み、チャットだけない**：チャット配信工程の問題の可能性
- **dailyだけ、またはREADMEまで更新**：途中停止・部分更新の可能性

### 対応

必要なら当日分を手動復旧する。手動実行でも対象期間は **前日18:31〜当日18:30 JST** のまま扱う。

> Scheduled Taskそのものが起動しなかった場合、そのタスク自身からエラー通知を出すことはできない。

---

## 2. 本文冒頭に「ルール読み込みエラー」が出た

表示例：

`⚠️ docs/daily_news_rules.md を読み込めなかったため、フォールバックルールで実行しました。`

### 現在の自動対応

- ニュース作成・チャット配信は継続
- GitHub保存も最低限のフォールバックで継続
- エラー文は daily・README・recent_index には保存しない
- この実行は「不具合あり」扱い
- **Issue #1への `@karipuri` 通知は送らない**

### 確認

- `docs/daily_news_rules.md` が `main` に存在するか
- ファイルが正常に読めるか
- GitHub接続・private repositoryへのアクセスに問題がないか

### 対応

原因を直したうえで次回の通常実行を確認する。当日本文自体が正常なら、必ずしもゼロから再生成する必要はない。

---

## 3. `recent_index.md` がない・壊れている・古い

### 影響

重複判定、継続ニュース判定、伏線回収候補の精度が落ちる。

### 対応

- 直近のdailyを確認して索引を再構築
- 原則直近7日分へ戻す
- 各日は見出し＋1行要約を基本にする
- 本文に存在しない新事実を索引へ足さない
- `recent_index.md` を事実確認ソースとして使わない

本文が正常なら、ニュース自体を作り直す必要はない。

---

## 4. 前日・一昨日のdailyを読めない

### 影響

- 重複ニュースを拾いやすくなる
- 継続ニュースの差分確認が弱くなる
- 過去本文の伏線回収を誤る可能性がある

### 対応

- 読めない過去本文を推測で補わない
- 伏線回収は行わない、または確認できる範囲だけにする
- 最新ニュース自体はウェブで確認する
- GitHub側の欠損・権限・パスを確認する

---

## 5. Web検索・ニュースソースの一部が取れない

### 対応

- 同じ事実を確認できる一次情報・別の主要報道へ切り替える
- 1候補に固執せず、確認不能なら候補から外す
- 件数合わせで未確認情報を入れない
- 速報で錯綜しているなら断定を避けるか別候補へ差し替える

一部ソース取得失敗だけで全体を事故扱いにする必要はない。最終的な確定本文の事実確認が成立しているかで判断する。

---

## 6. 最終ファクトチェックで誤りを発見した

### 保存前

通常工程として本文を修正・必要なら再生成し、その後に確定本文とする。

### 保存後

事実内容そのものの誤りなら、一部媒体だけ直して終わらせない。

1. 正しい事実を再確認
2. 確定本文を修正
3. dailyを修正
4. READMEを修正
5. recent_indexに影響があれば修正
6. 3媒体の整合性を再確認

---

## 7. dailyだけ更新された / READMEまでで止まった

これは**部分更新事故**。

### 確認

コミット履歴を時系列で見て、`daily → README → recent_index` のどこまで成功したか確認する。

### 対応

- dailyのみ成功：正しい当日本文を確認してREADME・recent_indexを復旧
- daily＋README成功：recent_indexを復旧
- 途中の内容が怪しい：先に確定本文との整合性を確認

3媒体が揃い、整合性確認が終わるまで `@karipuri` 通知は追加しない。

> どの媒体が正しいか不明なら、READMEを自動的に正本扱いしない。チャット本文・GitHub差分・コミット履歴・参照元を照合する。

---

## 8. dailyとREADMEの内容が違う

### 表示差だけなら正常

- 見出し階層
- dailyの生成日時・対象期間
- READMEの「毎日19時ごろ更新」
- Markdownリンク・ChatGPT引用形式

### ニュース内容が違えば事故

- 固有名詞・数値が違う
- 対戦相手・対象地域などが違う
- READMEだけ具体化・補足されている
- 結論や事実説明が別内容

### 対応

- 転記・変換ミス：確定本文を基準に該当媒体を修正
- 事実内容の訂正：daily・README・recent_indexの影響箇所を揃えて修正

---

## 9. recent_indexの内容がおかしい

例：当日分がない、7日を超えて不自然に残る、本文にない事実がある、継続テーマ・回収候補が噛み合わない。

### 対応

直近dailyと当日の確定本文を基準に索引を再構築する。本文が正常ならdailyやREADMEまで作り直さない。

---

## 10. GitHubに `cite...` や `navlist...` が残った

これは通常の文字化けではなく、ChatGPT画面専用の内部マーカーがGitHubへ保存された状態。

### 対応

- 内部引用マーカーを除去
- 「主な参照元」は通常のMarkdownリンクへ直す
- ニュース本文の事実内容は変更しない
- dailyとREADMEの両方を確認する

---

## 11. 同じファイルが複数回コミットされた

- **内容同一・実質差分なし**：基本的に実害なし
- **Markdown・表示修正だけ**：内容が整合していれば問題なし
- **ニュース事実が変わっている**：daily・README・recent_indexを照合

コミット回数だけで事故と判断しない。

---

## 12. GitHubのSHA競合・更新競合

### 意味

ファイルを読んだ後に別の更新が入り、手元のSHAが古くなった状態。古い状態で上書きして変更を消す事故を防ぐため、GitHubが更新を拒否することがある。

### 手動対応

1. 対象ファイルを再取得
2. 最新内容と最新SHAを確認
3. 既存変更を消さないように内容を確認・統合
4. 最新SHAで再更新

最新状態を確認せず古い内容で上書きしない。

---

## 13. GitHub接続・権限エラー

### 確認

- repositoryが `yuya228/news-archive` か
- private repositoryを読めるか
- `main` を参照できるか
- 必要な書き込み権限があるか
- GitHub接続自体が有効か

### 対応

復旧後、当日のコミット履歴を確認して不足分だけ直す。全部を無条件に再実行しない。

---

## 14. 想定外のrepository・pathへ書き込もうとした

重要度が高い事故。

### 対応

1. 自動運用をいったん止めることを検討
2. 実際にどこへ何を書いたか確認
3. 意図しない変更があれば差分確認
4. Scheduled Task・正本ルールの書き込み先指定を確認
5. 原因が分かるまで無理に再開しない

Scheduled Taskの許可された書き込み先は通常以下だけ。

- 当日の `daily/YYYY/MM/YYYY-MM-DD.md`
- `README.md`
- `daily/recent_index.md`
- Issue #1への当日更新通知コメント

---

## 15. `@karipuri` 通知が来ない

### 現在の正常通知条件

次をすべて満たす必要がある。

1. 正本ルールの読み込み成功
2. daily更新成功
3. README更新成功
4. recent_index更新成功
5. 3媒体の整合性確認完了

**19:00以降という条件は現在ない。** 5条件が揃えば、その時点で通知する。

### 対応

5条件が成立しているのに通知がない場合、Issue #1への通知処理だけ失敗した可能性を確認する。本文や3ファイルが正常なら、ニュースを再生成する必要はない。

### 旧仕様の注意

2026-08-21には、旧仕様で「19:00以降」という通知条件が残っていたため、3ファイル更新が19時前に完了して通知されない事象が起きた。現在はこの条件を廃止している。

もし今後同じ症状が出たら、Scheduled Taskや正本に**旧19:00待ち条件が残っていないか**確認する。

---

## 16. `@karipuri` が二重通知された

### 対応

- Issue #1の当日コメントを確認
- 本文・GitHub3ファイルが正常ならニュース再生成は不要
- 重複通知だけの問題として原因を確認する

不要コメントを削除するかはその時点で判断し、自動削除前提にはしない。

---

## 17. 通知済みの後で事実誤認を発見した

### 対応

まず本文とGitHub3媒体を正しく修正する。

1. 事実確認
2. 確定本文の修正
3. daily・README・recent_indexの再整合
4. 既存Issue通知を確認

**訂正通知を追加するか、既存通知をどう扱うかは事故ごとに判断する。** 通常の自動ルールとして勝手に追加しない。

---

## 18. Scheduled Task自体が途中で落ちた・実行されなかった

これはタスク内部のルールだけでは完全には検知できない。

### 確認

- Scheduled Taskの実行履歴
- `last_run_time`
- GitHubコミットの有無と時刻
- チャット配信の有無
- Issue #1通知の有無

### 注意

`last_run_time` は内部工程の正確な開始・終了時刻を示す詳細ログではない。GitHubコミット時刻と合わせ、外から分かる範囲で判断する。

---

# 事故時の短縮チェック

- **本文がない** → Task実行履歴 → GitHubコミット
- **本文冒頭にルールエラー** → 正本確認 → `@karipuri`通知なしが正常
- **daily / README / index が欠ける** → コミット履歴で停止地点確認
- **dailyとREADMEが違う** → 表示差か事実差か分類
- **事実差** → 確定本文を直して3媒体を揃える
- **表示差だけ** → 該当媒体だけ修正
- **GitHub内部引用マーカー** → マーカーだけ除去しMarkdownリンクへ
- **通知がない** → 正本読込＋3更新＋整合性の5条件を確認
- **対象期間確認** → 前日18:31〜当日18:30
- **想定外の書き込み先** → 原因確認まで自動運用再開を急がない

## 最後に

事故対応の目的は「とにかく再実行する」ことではなく、**正しいニュース本文と3媒体の整合性を最小限の修正で取り戻すこと**。

自動実行仕様を変える必要がある場合は、この障害対応メモだけを書き換えず、正本 `docs/daily_news_rules.md` と Scheduled Task の役割を分けて検討する。
